# 個人網站維護與內容同步作業規範

本網站原始碼為公開 GitHub 儲存庫 `DrWeiLinTCM/drweilinchang-site`，以 Astro 建置。**任何公開提交的內容（包括歷史紀錄）都可能被他人看到**。維護工作不需要網站、Facebook、vocus 或 GitHub 的帳號密碼。

## 一、職責與修改流程

1. 先在 `main` 最新版本以外建立工作分支，不直接推送 `main`。
2. 修改文章、圖片、樣式或程式後執行 `npm ci`、`npm test`，確認建置、搜尋索引、頁面和圖片完整。
3. 建立 Pull Request，列出修改檔案、主要風險、測試結果及預期畫面差異。涉及版面變更時附上電腦版／手機版預覽。
4. 由網站擁有者確認後才合併、部署。若正式網站異常，優先回復到上一次正常的提交。
5. 建議網站擁有者在 GitHub Settings → Rules/Rulesets 或 Branches 設定主分支保護、禁止直接推送、要求 PR 且測試通過。此文件與 CI 本身**不能**代替主分支保護。

## 二、FB／vocus → 網站的內容同步

網站文章存在 `src/content/cases/`（醫案）及 `src/content/articles/`（衛教），封面放在 `public/images/posts/`。

- 從使用者提供的原始 FB 粉專貼文連結、可合法讀取的公開貼文、使用者匯出的貼文資料，或獲正式授權的**最小必要權限**資料來源取得文章。公開頁面若無法讀取，必須回報，**不能猜測漏掉的貼文**。
- 先比對來源貼文 URL、標題、日期及內容主題，再判定「已有／缺少／待核對／暫不發布」；相似標題不代表同一篇。
- 新貼文先製作 Markdown 草稿，檢查格式、引用、圖片授權、個案匿名化與醫療宣稱，再送審。**不可把患者姓名、電話、病歷號、可識別影像、完整病歷等未核准資料上傳公開儲存庫**。
- `publishDate` 設為使用者確認的公開發文日期；首頁與文章頁面只顯示發布日期，**不要重新加回「更新於」日期文字**。既有網址／slug 不任意更改。
- 文章更新不得憑空補病史、捏造療效或將個案結果說成普遍療效。保留來源及臨床證據的界限。
- 未經核對，不承諾網站與 FB 的文章「數量完全一致」或「即時同步」；發文同步是獨立的來源存取與發布流程。

## 三、視覺設計與功能維護

- 全站設定在 `src/config.ts`；全域設計變數與響應式樣式在 `src/styles/global.css`。
- 維持既有品牌、導覽與預約入口可用；任何大改版應在 PR 中提供前後對照。
- 修改後檢查手機、平板與桌機的排版；避免圖片拉伸、文字溢出、點擊區太小、搜尋或文章連結失效。
- 不擅自更改看診資訊、醫師資料、療法說明、衛教內容與對外聯絡方式。

## 四、帳密、憑證和第三方服務安全

- 不在聊天、程式碼、PR、Issue、截圖、公開網站中輸入帳密、Cookie、存取 Token、API Key 或部署祕密。
- 優先使用現有 GitHub 連線，並限制在此單一儲存庫。Facebook／vocus 若需要取得非公開內容，以官方 OAuth／正式授權或使用者自行匯出為主；不因網站維護而持續保留主要帳號登入工作階段。
- 部署祕密使用部署平台的 Secret／Environment 管理，不存進原始碼。開啟帳號雙重驗證，定期檢查已連接的第三方應用與工作階段。
- `.github/workflows/site-quality.yml` 僅在 GitHub 執行建置與測試，使用唯讀 `GITHUB_TOKEN` 權限；**不會自動發布、登入社群或擁有任何社群帳號權限**。
- 若懷疑憑證已經被洩漏：立即撤銷工作階段／Token、更換受影響憑證、檢查異常提交與部署。把祕密從最新版本刪除，不代表已從 Git 歷史完全清除。

## 五、可重複的檢查清單

- [ ] 已比對 FB／vocus 來源、找到新內容與缺漏
- [ ] 未重複發文，日期與封面配對正確
- [ ] 內容有依據、匿名與影像授權完成檢查
- [ ] 沒有把密碼或個資加入公開儲存庫
- [ ] `npm test` 通過，網站搜尋與連結可用
- [ ] 修改透過 PR 送審，不直接更改正式版
